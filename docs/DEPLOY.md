# Обновление сайта и сервера

Всё, что нужно набрать. Команды однострочные — именно склейка нескольких строк
в одну ломала прошлые деплои.

## 1. Переменные окружения

Нужны только при первой настройке новых возможностей. Файл `/opt/vanillacoins/deploy/.env`,
после правки — обычный деплой из шага 3.

```
nano /opt/vanillacoins/deploy/.env
```

Что дописать (значения свои):

```
TELEGRAM_BOT_TOKEN=токен от @BotFather
TELEGRAM_BOT_USERNAME=VanillaCraftx_bot
TELEGRAM_WEBHOOK_SECRET=любая длинная строка, придумайте сами
TELEGRAM_CHAT_ID=-1003907771050
TOPMC_SERVER_ID=27567
TOPMC_KEY=ключ из кабинета мониторинга
```

Необязательное, у всего есть значения по умолчанию:

```
VOTE_REWARD_VC=200          # за голос
VOTE_STREAK_BONUS_VC=10     # за каждый день серии сверх первого
VOTE_STREAK_CAP=30          # дальше серия не оплачивается
VOTE_MAX_AGE_HOURS=48       # голоса старше не оплачиваются
PURGE_DROP_PERCENT=50       # сколько процентов баланса стоит смерть в судную ночь
BANNER_CACHE_DIR=/tmp/vc-banners  # где лежат собранные видеобаннеры партнёров
BANNER_CACHE_FILES=40             # сколько роликов держим, дальше вытесняем старые
```

Видеобаннеры собирает ffmpeg — он ставится в образ сайта, отдельной настройки
не требует. Кэш живёт внутри контейнера и очищается при пересборке: это не
потеря, ролик собирается заново за пару секунд.

## 2. Место на диске

Если сборка падала на нехватке места — сначала уборка:

```
bash /opt/vanillacoins/deploy/cleanup.sh
```

Посмотреть, кто съел диск, ничего не удаляя:

```
bash /opt/vanillacoins/deploy/diskcheck.sh
```

## 3. Обновление сайта

Одна команда: код с ветки, чистка, миграции базы, пересборка, уборка за собой.

```
bash /opt/vanillacoins/deploy/update.sh
```

Другая ветка — через переменную:

```
BRANCH=main bash /opt/vanillacoins/deploy/update.sh
```

## 3.1. Каталог: косметика, кейсы, товары магазина

`update.sh` накатывает только схему базы. Косметика, коллекции, кейсы и товары
магазина живут в каталоге (`web/prisma/*.mjs`) и заезжают отдельной командой:

```
bash /opt/vanillacoins/deploy/seed.sh
```

Нужна после любой правки цен кейсов, набора косметики или магазина. Без неё
сайт соберётся с новым кодом, но покажет старый каталог.

Отдельно от `update.sh` — потому что каталог перезаписывает и то, что можно
менять в панели: цена товара, его описание и флаг «в продаже» вернутся к
значениям из репозитория. Правку из панели после прогона придётся повторить.

История открытий кейсов при этом не страдает: содержимое кейса сверяется
построчно, а не пересоздаётся. Иначе каждый прогон стирал бы записи provably
fair и отметки о бесплатном ящике — и суточный кейс открывался бы всем заново.

Проверить, что поднялось:

```
docker compose --env-file /opt/vanillacoins/deploy/.env -f /opt/vanillacoins/deploy/docker-compose.yml ps
```

Посмотреть логи сайта, если что-то не так:

```
docker compose --env-file /opt/vanillacoins/deploy/.env -f /opt/vanillacoins/deploy/docker-compose.yml logs --tail=100 web
```

## 3.2. Технический сайт tech.vanillacraft.click

Стенд, на который обновления приезжают раньше боевого. Та же сборка, отдельная
база `vanilla_tech`, вход только по списку.

Разовая настройка:

1. Запись DNS: `tech` → 92.246.137.26 (тип A, как у основного домена).
2. В `deploy/.env` дописать, кому открыт стенд:

```
STAGING_LOGINS=rym6a
```

3. Обновить Caddy — блок для поддомена уже в `Caddyfile.domain`:

```
cd /opt/vanillacoins/deploy && cp Caddyfile.domain Caddyfile && docker compose --env-file .env restart caddy
```

Дальше обновление стенда одной командой:

```
bash /opt/vanillacoins/deploy/tech.sh
```

Другая ветка — через переменную:

```
BRANCH=имя-ветки bash /opt/vanillacoins/deploy/tech.sh
```

Скрипт заводит базу стенда, если её ещё нет, накатывает схему с каталогом и
поднимает контейнер на порту 3001. Боевой стек он не трогает: у стенда своё имя
проекта `vc-tech`.

Postgres у стенда общий с боевым — не из-за лени, а из-за памяти: второй сервер
базы на этой машине стоил бы 150–250 МБ впустую. Данные при этом разведены:
стенд работает с `vanilla_tech` и боевую базу не видит.

Кассы, Telegram и панель хостинга на стенде выключены переменными: стенд не
должен принимать настоящие платежи, писать в общий чат и трогать игровой сервер.

## 3.3. Выкатка боевого сайта из панели

Кнопка живёт в панели основного сайта, раздел «Выкатка», и доступна только
логинам из `RELEASE_LOGINS`. Она не выкатывает сама, а ставит задачу в очередь:
работу делает агент на VPS.

Так — а не наоборот — потому что иначе контейнеру сайта пришлось бы дать доступ
к docker и git на хосте, и любая дыра в сайте превращалась бы в выполнение
команд на сервере.

Разовая настройка:

1. Придумать длинный токен и дописать в `deploy/.env`:

```
DEPLOY_AGENT_TOKEN=длинная-случайная-строка
RELEASE_LOGINS=rym6a
```

2. Поставить агента в cron:

```
crontab -e
```

и добавить строку:

```
* * * * * /opt/vanillacoins/deploy/release-agent.sh >> /var/log/vc-release.log 2>&1
```

3. Применить `.env` к сайту:

```
bash /opt/vanillacoins/deploy/update.sh
```

Проверить агента вручную можно так — он сам скажет, если токена нет:

```
bash /opt/vanillacoins/deploy/release-agent.sh
```

Маршруты `/api/deploy/*` закрыты в Caddy: агент ходит на `127.0.0.1:3000`
напрямую, а снаружи лишний вход к выкатке боевого сайта не нужен.

Плагин игрового сервера кнопка не обновляет. Новый jar по-прежнему заливается
руками при остановленном сервере — галочка «перезапустить игровой сервер» умеет
только перезапуск.

## 3.4. Разовый перевод осколков в VC

Только один раз, при выкатке обновления, в котором осколки убраны:

```
cd /opt/vanillacoins/deploy && docker compose --env-file .env --profile tools run --rm --build migrator node scripts/shards-to-vc.mjs
```

Каждому игроку начисляется по одному VC за три осколка, начисление попадает в
его историю операций. Повторный запуск ничего не делает: отметка о переводе
лежит в настройках, без неё второй прогон выплатил бы всем ещё раз.

Порядок важен: сначала `update.sh` и `seed.sh` (каталог переводит цены и
награды в VC), потом эта команда.

## 4. Вебхук Telegram

Один раз после того, как задан `TELEGRAM_WEBHOOK_SECRET` и сайт задеплоен.

Значения достаём из файла, а не через `source`: `source` выполняет файл как
скрипт, и ключ со знаком `&` внутри (такие есть у касс) рвёт строку — часть
значения уходит в фоновую задачу, остаток выполняется как команда, а переменная
остаётся пустой. Docker Compose читает тот же файл своим разборщиком, поэтому
ему такие значения не мешают — ломается только `source`.

```
cd /opt/vanillacoins/deploy && TGTOKEN=$(grep -m1 '^TELEGRAM_BOT_TOKEN=' .env | cut -d= -f2-) && TGSECRET=$(grep -m1 '^TELEGRAM_WEBHOOK_SECRET=' .env | cut -d= -f2-) && curl -sS -F "url=https://vanillacraft.click/api/tg/webhook" -F "secret_token=$TGSECRET" -F 'allowed_updates=["message","chat_join_request"]' "https://api.telegram.org/bot$TGTOKEN/setWebhook"
```

`allowed_updates` перечислен явно: без `chat_join_request` бот не увидит заявок
на вступление в группу. Ему также нужно право «Добавлять участников».

Проверить, что Telegram доволен:

```
cd /opt/vanillacoins/deploy && TGTOKEN=$(grep -m1 '^TELEGRAM_BOT_TOKEN=' .env | cut -d= -f2-) && curl -sS "https://api.telegram.org/bot$TGTOKEN/getWebhookInfo"
```

В ответе не должно быть `last_error_message`. Главная проверка — написать боту
`/start`: если он ответил, секрет совпал.

## 5. Игровой сервер

Плагин обновляется только при остановленном сервере: Java читает классы из jar
лениво, и подменённый на ходу файл ломает уже работающий процесс — игроки видят
«unexpected error» на командах.

Порядок в панели `mgr.bisquit.host`: остановить сервер → заменить
`plugins/VanillaCore-1.0.0.jar` → запустить.

Иконка сервера в списке — `server-icon.png` в корне сервера, ровно 64×64.
Её можно заливать и на работающий сервер: это картинка, а не классы, — но
покажется она только после перезапуска, потому что читается при старте.

Остановку проверяем по `uptime`, а не по полю `state`. Во время долгой паузы
(например, десятисекундного зависания watchdog) панель успевает показать
`state: offline` у работающего сервера — на этом уже один раз попались и
залили jar под живой процесс. Растущий `uptime` в `resources` означает, что
сервер не останавливался, чем бы ни было `state`.

Сайт обновляем **до** запуска сервера: плагин при старте идёт за новыми
маршрутами API, и на старой сборке сайта они ответят 404.

## Чего делать нельзя

`docker system prune --volumes` и `docker volume prune` на этой машине сносят
том `pgdata` вместе с базой сайта. Скрипты деплоя тома не трогают никогда.
