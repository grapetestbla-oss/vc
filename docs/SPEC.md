# VanillaCoins — спецификация проекта

Ванильный Minecraft-сервер без приватов + сайт с личным кабинетом, донат-валютой,
кейсами, мини-играми и админ-панелью.

## Компоненты

| Компонент | Технологии | Где живёт |
|---|---|---|
| `plugin/` | Java 21, Paper 26.2 API | игровой хостинг Bisquit (`saw-point`) |
| `web/` | Next.js 15 (App Router), TypeScript, Prisma | VPS |
| PostgreSQL | 16 | VPS (docker) |
| Redis | 7 | VPS (docker), сессии краша и rate-limit |

Плагин **не ходит в базу напрямую** — только в HTTP API сайта с server-токеном.
Вся бизнес-логика (баланс, кейсы, промокоды, наказания) в одном месте, плагин
остаётся тонким клиентом. Это упрощает аудит денег и не даёт игровому серверу
доступа к паролям.

## Решения, принятые заказчиком

- `online-mode=false`, свои логин/пароль. Пиратские клиенты пускаются.
- VC **не выводятся** в деньги и **не передаются** между игроками.
- Из модов только Simple Voice Chat. HWID-бан невозможен → идентификация по
  аккаунту и IP.
- Полёт админов — команда `/spec`, не хоткей.

## Аккаунт и авторизация

Регистрация только на сайте: логин (= ник в игре), email, пароль.

1. Игрок заходит на сервер под своим ником.
2. Пока не авторизован: заморожен, слепой (эффект blindness), чат и команды
   кроме `/login` заблокированы, 60 секунд на ввод.
3. `/login <пароль>` → API проверяет argon2id-хэш.
4. Если IP не встречался у этого аккаунта раньше — требуется `/2fa <код>`.
   Код (6 цифр, TTL 10 минут) генерируется в личном кабинете на сайте.
5. Три неверных пароля подряд → кик и отметка в логах; 10 неверных с одного IP
   за час → временная блокировка IP на вход.

Пароли: argon2id, соль на пользователя. Плагин никогда не видит хэш — отправляет
пароль по HTTPS на API и получает вердикт.

### Уровень аккаунта

Растёт от наигранного времени: `level = floor(sqrt(hours_played))`, максимум 50.
Уровень 3 ≈ 9 часов игры — порог для активации промокода медиапартнёра.

**Награда за прокачку.** Пороговые уровни платят разово: 5 — 500 VC, 10 — 1000,
20 — 2000, 30 — 5000, дальше по 1000 VC за каждый новый уровень. Уровень нигде
не хранится (он считается из времени), поэтому «момент повышения» ловить негде:
в `User.rewardedLevel` держим планку — до какого уровня уже заплачено. Каждый
тик наигранного времени сверяет её с текущим уровнем и добирает всё, что между
ними, так что пропуск нескольких уровней за один тик ничего не теряет.

`rewardedLevel = null` означает, что игрока эта система ещё не видела: планка
ставится по текущему уровню без выплаты. Иначе после включения наград все, кто
уже наиграл свои уровни, получили бы их задним числом одной кучей.

## Наказания

| Команда | Кто | Эффект |
|---|---|---|
| `/ajail <ник> <причина> <минуты>` | helper+ (≤60 мин), admin+ (без лимита) | Деморган |
| `/warn <ник> <причина>` | admin+ | Варн на 7 дней |
| `/ban <ник> <причина> <дни>` | admin+ | Бан аккаунта + IP |

- **Деморган**: время идёт **1 к 10** — срок 60 минут отбывается за 6 минут
  реального времени. Тикает только пока игрок онлайн. Добыча породы ускоряет.
- **Варн**: активен 7 дней. Второй активный варн автоматически превращается в
  бан на 5 дней.
- **Бан**: закрывает вход по аккаунту и по всем IP, с которых он заходил за
  последние 30 дней. HWID недоступен — своего лаунчера нет.

Бан по IP бьёт по соседям за NAT. Поэтому IP-блок мягкий: при совпадении
только по IP (аккаунт чистый) игрок получает 2FA-проверку, а не отказ.

## Уровни админки

| Ур. | Название | Префикс | Права |
|---|---|---|---|
| 1 | media | — | Красный ESP на себе (виден другим), `/spec`, локальные время и погода |
| 2 | helper | `HELPER` | Жёлтый ESP, `/spec`, `/esp`, `/ajail` ≤60 мин, `/tp`, `/tphere`, `/reports`, `/asms` |
| 3 | administrator | `ADMIN` | Всё от helper + `/warn`, `/ban`, `/check`, доступ в админ-панель (выдаёт 5 ур.) |
| 4 | pr assistant | `PR` | Всё от admin + расширенные данные в панели |
| 5 | chief administrator | `Chief Admin` | Всё + выдача админок, промокоды, бонус-коды, `/news`, op |

ESP — свечение (`Glowing`) сквозь стены: медиа светятся красным для всех,
админы 2+ — жёлтым для админов. `/esp` показывает игроков и админов **строго
ниже своего уровня**.

## Экономика

**VanillaCoins (VC)** — единственная валюта. Покупается за рубли, не выводится.

Курс пополнения: **1 ₽ = 2 VC** (меняется переменной `VC_PER_RUB`).

Источники VC: пополнение на сайте, промокоды, бонус-коды, ежедневный вход,
дневная норма игры, награды за уровень, голоса в мониторинге.
Траты: кейсы, косметика, мини-игры, магазин удобств, точки дома.

### Точки дома

Первую даёт покупка «Точка дома» в магазине. Каждые пять уровней аккаунта
открывают ещё одну, и открытую нужно докупить: первая докупка — 2000 VC, каждая
следующая на 500 VC дороже. Уровень открывает возможность, VC её оплачивают —
поэтому десять домов на старте не появятся ни за какие деньги.

Координаты живут в `PlayerHome` на сайте, а не в мире сервера: их считает и
ограничивает сайт (`GET`/`POST /api/mc/homes`), плагин только показывает и
телепортирует. Единственная точка старой покупки лежала в состоянии товара —
при первом чтении она переносится в `PlayerHome` под именем «дом».

### Пополнение баланса

Кассы подключаются в панели: раздел «Платёжные системы», только 5 уровень.
Там же хранятся ключи и задаётся бонус — надбавка к VC за оплату через эту
кассу (14% — за 1000 ₽ игрок получит 2280 VC вместо 2000). Настройки лежат в
таблице `Setting` и применяются сразу; переменные окружения
(`FREEKASSA_*`, `PLATEGA_*`) остаются значениями по умолчанию для нового
сервера. Пока не подключена ни одна касса, сам собой показывается ручной
режим с заявками.

**FreeKassa.** Ссылка на оплату подписывается первым секретом:
`md5(магазин:сумма:секрет1:валюта:заказ)`, номером заказа служит id платежа.
Уведомление приходит на `/api/payments/freekassa` и проверяется трижды: адрес
отправителя из списка `FREEKASSA_IPS`, подпись `md5(магазин:сумма:секрет2:заказ)`
вторым секретом и сумма не меньше выставленной. Только после этого начисляются
VC и доля партнёра.

Обработка идемпотентна: FreeKassa повторяет уведомление, пока не получит
«YES», поэтому статус меняется условным обновлением — повтор подтверждается,
но второй раз ничего не начисляет. Все отказы (чужая подпись, неизвестный
заказ, недоплата) пишутся в журнал.

**Платега.** Счёт создаётся запросом `POST /v2/transaction/process` с ключами в
заголовках `X-MerchantId` и `X-Secret`; id платежа уходит в поле `payload`.

Версия важна. Старый `/transaction/process` требует `paymentMethod`: без него
он отвечает отказом («No available card cascades»), при этом транзакция у кассы
уже заведена. Получалась худшая из комбинаций — игрок видел «касса не
отвечает», а касса потом слала уведомление о счёте, которого у нас нет. В v2
способ оплаты необязателен — его выбирает игрок на странице кассы, — а ссылка
приходит в поле `url` вместо `redirect`. Путь вынесен в настройки
(`PLATEGA_PATH`) и правится без пересборки.

Уведомление приходит на `/api/payments/platega` с теми же заголовками — по ним
касса и опознаётся, отдельной подписи в её протоколе нет. Начисляем только по
статусу `CONFIRMED` и только если сумма не меньше выставленной; сумму читаем и
из `paymentDetails.amount`, иначе ноль сравнивался бы с суммой счёта и оплата
отбивалась бы как недоплата. `CANCELED` закрывает счёт, чтобы он не висел у
игрока. Обработка идемпотентна.

Счёт, для которого не удалось получить ссылку, остаётся в ожидании, а не
закрывается: отказ мог случиться уже после того, как касса завела транзакцию, и
на закрытый счёт пришедшие деньги зачислить было бы нельзя. Неизвестный заказ
пишется в журнал вместе с телом уведомления — иначе не видно, какими полями
касса его прислала.

**Досверка.** Уведомление — не единственный источник правды: оно может не дойти
или прийти позже, и тогда игрок видит оплаченный счёт у кассы и ничего у нас,
а ждать приходится, пока счёт протухнет. Поэтому статус спрашиваем сами —
`GET /transaction/{id}`:

- игрок вернулся с кассы на `/topup?paid=1` — страница проверяет сразу и молча,
  повторяя через пять секунд; там же есть кнопка «Проверить оплату»;
- плагин раз в пять минут дёргает `/api/mc/payments` — на случай, если вкладку
  закрыли.

Зачисляет всё та же `creditPayment` с условным обновлением, поэтому досверка и
уведомление, пришедшие одновременно, не начислят дважды. `CANCELED`, `EXPIRED`
и `FAILED` закрывают счёт, чтобы он не висел в ожидании.

**Разбор в панели — только для ручных заявок.** Счета касс подтверждает касса:
одобрение руками означало бы выдачу VC до того, как деньги дошли, и повторную
выдачу, когда придёт уведомление или досверка. В панели они показаны отдельным
списком «Ждут кассу», без кнопок, а API отвечает отказом на попытку разобрать
такой счёт.

**Ручной режим** остаётся запасным путём и работает так:

1. Игрок на `/topup` указывает сумму в рублях, способ перевода, контакт и
   комментарий. Одновременно открытой может быть только одна заявка.
2. Заявка попадает в панель, раздел «Пополнения» — он виден только 5 уровню.
3. Чиф-администратор сверяет перевод и одобряет либо отклоняет с
   комментарием. VC начисляются только при одобрении, повторное одобрение
   одной заявки невозможно.

Игрок видит статус своих заявок на той же странице `/topup`.

### Доля медиапартнёра

Когда администрация подтверждает пополнение игрока, партнёр, чей промокод
привязан к этому аккаунту, автоматически получает **10 % VC** от начисленной
суммы (`PARTNER_SHARE_PERCENT`). Считается только от пополнений за деньги: с
бонусов и промо-наград доля не идёт, иначе партнёр накручивал бы баланс через
собственные коды. Со своего пополнения партнёр доли тоже не получает.
Заработок виден в кабинете партнёра, каждая выплата — отдельная транзакция
`PARTNER_SHARE`.

### Инструменты партнёра

В кабинете партнёра, кроме статистики и заработка, лежат две вещи:

- **Готовый баннер.** Макет с артом сервера, в который браузер подставляет
  промокод партнёра: старый текст на табличке затирается куском её же фона,
  поверх рисуется настоящий код — крупным шрифтом с чёрным контуром, тёмной
  копией со сдвигом вместо объёма и вертикальным градиентом заливки, как в
  самом макете. Строка с наградой перерисовывается, только если условия
  промокода разошлись с зашитыми в картинку (1000 VC на 3 уровне) — при
  стандартных условиях арт не трогаем. Скачивается как PNG 1376×768. Шрифт
  (Russo One, OFL) лежит у нас в `public/fonts` — сборка не должна зависеть
  от чужого CDN.
- **Ссылка для описания канала** вида `vanillacraft.click/r/КОД`. Открывает
  регистрацию с уже подставленным промокодом: игроку не нужно ничего вводить
  руками. Код в ссылке приводится к верхнему регистру, поле остаётся
  редактируемым — привязка всё равно происходит один раз и навсегда.

### Магазин за VC

Раздел `/shop`. Продаются только удобства — ни оружия, ни ресурсов, ни защиты
в бою, чтобы донат не ломал ваниллу:

| Товар | Цена | Что даёт |
|---|---|---|
| Телепорт к игроку ×5 | 500 VC | `/tpa <ник>`, заряд списывается только при согласии цели |
| Возврат на место смерти ×5 | 400 VC | `/back` в течение 15 минут после смерти |
| Точка дома | 1500 VC, уровень 2 | `/sethome` и `/home`, кулдаун 30 минут, навсегда |
| Карманный эндер-сундук ×10 | 300 VC | `/ec` |
| Верстак с собой ×10 | 150 VC | `/craft` |
| Страховка инвентаря ×1 | 900 VC | Автоматически сохраняет вещи и опыт при следующей смерти |

Заряды складываются: вторая покупка «телепорта ×5» даёт десять использований.
Списывает заряды сайт, а не плагин, — перезаход на сервер не возвращает
потраченное. В деморгане все эти команды выключены.

Таблица выше — только первое наполнение из `prisma/shop.mjs`. Дальше витрина
живёт в базе и правится в панели: раздел «Магазин», только 5 уровень. Там
меняются цена, название, описание, раздел, тип (заряды или навсегда), число
использований, нужный уровень и порядок на витрине, добавляются и скрываются
товары. Рядом с каждым товаром видно, сколько раз его купили и на сколько VC.

Поле «возможность» (`payload.feature`) — то, что ищет плагин: `tp`, `back`,
`home`, `enderchest`, `craft`, `keepinv`. Новую возможность сначала учат
плагин, иначе товар купят, а команда не заработает. Купленный товар удалить
нельзя — только убрать с витрины: удаление отняло бы у игроков оплаченные
заряды. Новая цена действует только на новые покупки.

### Открытие кейсов на сайте

За один раз открывается до пяти кейсов: `/api/cases/open` принимает `count`
1–5 и крутит каждый отдельно — свой сид, свой гарант, своё списание. Если VC
кончились посреди пачки, возвращаются уже открытые кейсы и причина остановки:
за неоткрытые деньги не списаны.

Барабан крутится только для одиночного открытия и только когда не включён
быстрый режим — четыре секунды на каждый из пяти кейсов никому не праздник.
Быстрый режим запоминается в браузере.

### Деморган и наряды

Минута срока стоит десяти реальных минут и идёт, только пока игрок онлайн, —
пересидеть час наказания стоит десяти часов в игре. Быстрый путь один: работа.
В зоне стоит прораб, он выдаёт наряды («наломать столько-то блоков», «собрать
мусор»), каждый закрытый наряд снимает минуту срока, между нарядами минута
перерыва. Добытый блок породы дополнительно списывает 5 секунд.

Ничего, кроме списания срока, наряды не дают: заключение не должно
превращаться в ферму ресурсов, поэтому ни дропа, ни опыта, ни предметов.

### Ранги администрации

Уровень админки остаётся числом 1–20: по нему считается старшинство (наказать и
снять наказание можно только тому, кто ниже) и его же читает плагин. Всё
остальное — название ранга, метка в чате, её цвет и набор прав — правится в
панели, раздел «Ранги и права» (право `ranks.manage`, по умолчанию 5 уровень).

Права — это ключи вида `payments.review` или `punish.lift`; каждая страница и
ручка панели проверяет свой ключ. Пока ранг не правили, набор прав совпадает с
прежними уровнями, поэтому поведение не меняется. Ранг с пустым списком прав
получает права по умолчанию для своего уровня — забытая галочка не оставляет
персонал без панели.

Встроенные ранги 1–5 переименовываются, но не удаляются: на них завязаны
проверки уровня. Новый ранг занимает свободный уровень; удалить его можно,
только когда на нём никого нет. У своего ранга нельзя снять вход в панель и
правку рангов — иначе панель запирается снаружи.

### Кейсы и косметика

Внутри кейсов — только то, что **видно другим игрокам**, и ничего, что даёт
преимущество:

| Вид | Что это | Как работает в игре |
|---|---|---|
| Шлейф | Дорожка частиц за игроком | Частицы четыре раза в секунду |
| Аура | Кольцо частиц вокруг | Вращается вокруг игрока |
| Питомец | Лисёнок, аксолотль, пчела, аллай | Неуязвим, без ИИ, ничего не подбирает |
| Шляпа | Торт, фонарь, маяк, яйцо дракона | Слот шлема, брони не даёт, надевается только в пустой слот |
| Эффект входа | Звук и вспышка при заходе | Молния только визуальная, без урона |
| Цвет ника | Цвет в чате и списке игроков | — |
| Титул | Надпись над головой | Отдельная сущность-пассажир, видна всем |
| Метка в мире | Именной маяк на спавне, строка в летописи | Ограниченный тираж |

Механики, которые держат интерес:

- **Ежедневный ящик** — одно бесплатное открытие в сутки.
- **Гарант.** Счётчик открытий без легендарки виден на кейсе. Дошёл до предела —
  легендарка выпадает принудительно.
- **Дубли → осколки.** 30 / 90 / 300 / 900 осколков по редкости.
- **Магазин за осколки.** Конкретный предмет покупается без случайности.
- **Коллекции.** Собрал набор — получил предмет, которого нет ни в одном кейсе.
- **Тираж.** У части предметов ограниченное число экземпляров, владелец получает
  свой номер.
- **Сезоны.** Кейс живёт сезон; после него предметы больше не выпадают.

Шансы каждого предмета показаны в интерфейсе. Реализация — provably fair:
`item = HMAC(server_seed, client_seed:nonce)`, хэш server_seed публикуется до
открытия, сам seed раскрывается при ротации.

### Мини-игры

Стол общий для всех: раунд длится 30 секунд — 20 на ставки, 10 на розыгрыш и
показ результата. Номер раунда считается от эпохи, поэтому расписание одинаково
для любого процесса сайта и не требует отдельного планировщика: первый же
запрос доигрывает просроченные раунды и открывает текущий.

- **Рулетка**: 41 равный сектор — 20 по x2, 15 по x3, 5 по x5 и один x10,
  перемешанные так, чтобы одинаковые не стояли блоками. Пустых секторов нет:
  выпавший сектор умножает ставку каждого, минимум x2. Колесо на клиенте
  крутится ровно к выпавшему броску (целое число оборотов плюс угол броска).

  **Средняя выплата такой раскладки — 2.93 ставки**, то есть рулетка отдаёт
  почти втрое больше, чем принимает; RTP из настроек на неё не действует. Это
  решение владельца сервера. Если понадобится вернуть управляемую экономику,
  менять надо раскладку `ROULETTE_LAYOUT` в `web/src/lib/live.ts`.
- **Краш**: точка вывода выбирается до старта, ракета летит до точки краха.
  Крах считается на сервере в момент закрытия ставок — анимация просто
  проигрывает готовый результат, подсмотреть и успеть поставить нельзя.

Всем видно, кто и сколько поставил в текущем раунде. История последних 15
раундов открыта: по раскрытому сиду результат пересчитывается вручную.

Обе — provably fair по той же схеме. RTP настраивается (по умолчанию 95%).
Ограничение одно — минимальная ставка (10 VC): ставка должна быть целым
положительным числом. Потолка ставки, дневного лимита проигрыша и паузы после
серии проигрышей нет — по решению владельца сервера. Аномальные серии
выигрышей по-прежнему попадают в «Срабатывания» админ-панели.

### Промокоды медиапартнёров

Код привязан к партнёру. Игрок вводит его **один раз** — при регистрации на
сайте или командой `/promo <код>` в игре, если при регистрации не ввёл. Сменить
код потом нельзя: иначе атрибуцию начинают перепродавать.

Награда (1000 VC) приходит не сразу, а когда аккаунт дорастает до 3 уровня —
это отсекает мультоводов, которые регистрируются ради выплаты. Проверка идёт
при каждом обновлении наигранного времени.

Партнёр видит в личном кабинете активации своего кода; игрок видит статус
награды («придёт на 3 уровне — сейчас у вас 1»).

### Заявки медиа-партнёров

Страница `/partners`: критерии по площадкам и форма заявки (площадка, ссылка на
канал, охваты, контакт, желаемый промокод). Одна активная заявка на аккаунт.

Разбор — в панели `/panel/partners`, решение принимают с 4 уровня. Одобрение
выдаёт статус media (1 уровень) и создаёт промокод партнёра; отказ пишется с
комментарием, который игрок видит в кабинете.

Минимальные критерии: YouTube — 50+ средних просмотров; YouTube Shorts и
TikTok — 3000+ просмотров за 7 дней по аналитике канала на тематике Minecraft;
Twitch — 15+ средних зрителей в месяц; Trovo — 10+; Discord — 500+ участников;
RuTube, VK Клипы, Telegram и группы ВКонтакте — индивидуально.

### Бонус-коды

Создаются в админ-панели: код, награда в VC, лимит использований, срок действия.
Активация в игре: `/bonus <код>`.

## Разбан

Публичная форма `/appeal` — без входа на сайт: забаненный аккаунт в игру не
пускают, а пароль от сайта он может и не помнить. Игрок указывает ник, контакт
и описывает ситуацию (не меньше 20 символов). Одно открытое заявление на ник,
не больше трёх заявлений с одного адреса в час.

Заявления разбирает **только 5 уровень** в разделе «Разбаны»: рядом с текстом
видно карточку игрока, его активные наказания и IP подачи. Одобрение снимает
все активные баны аккаунта и пишется в журнал, отказ сохраняет ответ игроку.

## Обнуление аккаунта

Действие в карточке игрока, доступно **только 5 уровню**. Обнуляет баланс,
осколки, наигранное время, косметику, историю кейсов, ставок и покупок
магазина; инвентарь, эндер-сундук и опыт в игре чистит плагин по поручению с
сайта (если игрок офлайн — при первом входе). Наказания и журнал остаются:
ради них обнуление и делают. Списанный баланс проходит транзакцией
`ADMIN_ADJUST` с причиной, само действие требует ввести ник игрока руками.

## Документы и согласия

На сайте лежат «Пользовательское соглашение» (`/terms`) и «Политика
конфиденциальности» (`/privacy`), редакция от 26 августа 2026. При регистрации
обе галочки обязательны: без них форма не отправляется, а API отклоняет запрос
даже при прямом обращении — иначе подтверждение ничего не стоило бы. Момент
согласия пишется в `User.acceptedTermsAt`.

## Обращения в поддержку

Раздел `/tickets` — только для зарегистрированных. Игрок создаёт обращение
(тема и сообщение), переписка идёт на сайте. Одновременно можно держать не
больше трёх открытых обращений, не больше 20 сообщений в час.

Разбирает обращения **только 5 уровень** в разделе «Обращения»: рядом с
перепиской видно ник, баланс и ссылку на карточку игрока. Ответ администрации
переводит тикет в статус «Есть ответ», сообщение игрока — обратно в «Ждёт
ответа», так в панели видно, чья очередь. Закрыть обращение может и игрок, и
администрация; в закрытое писать нельзя.

## Игры и кейсы на сервере

**Кости.** `/cubes <сумма>` вызывает ближайшего игрока в радиусе 8 блоков
(`dice.radius`), тот отвечает `/cubes accept` или `/cubes deny`. Оба бросают
кубик, броски видят все вокруг, больший забирает банк — обе ставки. Ничья
возвращает ставки.

Деньги двигает сайт: перед броском обе ставки списываются и лежат «в банке»,
после броска победителю уходит двойная ставка. Иначе проигравший успел бы
потратить VC между броском и выплатой. Партия, зависшая дольше пяти минут
(например, сервер упал между броском и выплатой), возвращает ставки сама.
Плагин суммы не считает — он только сводит игроков и сообщает броски.

**Кейсы в игре.** `/cases` показывает витрину с ценами, `/cases <ключ>`
покупает: VC списываются сразу, а кейс кладётся в инвентарь помеченным
сундуком. Игрок ставит его блоком — над блоком крутятся предметы, через
несколько секунд сайт считает выпадение и объявляет приз. Списание и
выпадение разнесены: покупка создаёт «билет», открытие его гасит, поэтому
второй раз за один кейс не спишут и дважды его не открыть. Если открытие
сорвалось, предмет возвращается в инвентарь.

**Объявление о редкой находке.** Выпал предмет эпической или легендарной
редкости — неважно, на сайте или в игре, — и в игровой чат уходит объявление
всему серверу. Технически это поручение в той же очереди, что и очистка
инвентаря: сайт кладёт его при выдаче предмета, плагин забирает и объявляет.

## Розыгрыши

Раздел `/giveaways` и вкладка «Розыгрыши» в шапке. У каждого розыгрыша своё
условие по наигранному времени (по умолчанию 15 часов). Игрок видит полосу
прогресса «наиграно X ч из Y» и кнопку участия, которая разблокируется при
выполнении условия.

Условие проверяется **дважды**: при подаче заявки и в момент розыгрыша — иначе
приз мог бы уйти тому, кому обнулили аккаунт после набора часов. Победителя
выбирает сервер: генерируется случайный сид, победитель считается как
`HMAC(сид, id розыгрыша) mod число участников`. Сид и число участников
публикуются на странице розыгрышей — результат пересчитывается вручную,
«рукой» победителя не назначить.

Управление — раздел панели «Розыгрыши», **только 5 уровень**: создание
(название, приз, описание, часы, срок приёма заявок), список заявок с часами
каждого участника, кнопки «Разыграть» и «Отменить» с подтверждением.

В игре плагин раз в 15 минут и при входе показывает плашку: что разыгрывают,
условие, сколько игрок наиграл и сколько осталось. Команда `/giveaway`
показывает то же самое по требованию. Часы берутся с сайта — той же цифрой,
что видна в кабинете.

## Управление мини-играми

Раздел панели «Мини-игры», **только 5 уровень**: рулетка и краш включаются и
выключаются на ходу. Выключенная игра перестаёт принимать ставки — и на сайте,
и через API, — но раунды продолжают разыгрываться, а ставки, сделанные до
выключения, выплачиваются как обычно: деньги игроков зависать не должны.
Выключенная игра исчезает с сайта целиком: карточка пропадает с витрины
`/games`, её страница отвечает 404. Когда выключены обе, из шапки пропадает
и сам пункт «Игры», а `/games` тоже отдаёт 404. Игрок, уже открывший стол,
видит плашку вместо формы ставки — страница не ломается под ним.

В панели рядом с переключателями виден оборот за сутки: сколько поставлено,
сколько выплачено и каков итог заведения.

## Технические работы

Включает и выключает **только 5 уровень** в разделе «Техработы». Пока режим
включён:

- на сайте все ниже 5 уровня видят заглушку вместо любой страницы — проверка
  живёт в middleware, поэтому содержимое закрытых страниц вообще не рендерится;
- открытыми остаются `/login`, `/panel`, `/maintenance` и API плагина: иначе
  чиф не смог бы войти и выключить режим;
- игровой сервер кикает всех, кроме 5 уровня, с указанной причиной и не пускает
  новых — плагин спрашивает состояние раз в 10 секунд.

Причина техработ задаётся в панели и показывается и на сайте, и в кике.

## Админ-панель

Отдельный раздел сайта, доступ с 3 уровня, вход тот же аккаунт + обязательная 2FA.

- **Логи**: все действия админов (кто, кому, что, когда, с какого IP), все
  наказания, все движения VC, входы и неудачные попытки входа.
- **Аккаунты**: карточка игрока — история наказаний, IP, время игры, баланс,
  транзакции, связанные аккаунты по IP.
- **Подозрительные срабатывания**: мультиаккаунты по IP, аномальные выигрыши в
  мини-играх, всплески начислений VC, вход с нового гео, серии неудачных
  авторизаций.
- **Статистика**: онлайн, регистрации, выручка, конверсия промокодов.
- **Управление** (5 уровень): выдача и снятие админок, создание промо- и
  бонус-кодов, правка награды и уровня у существующих промокодов (уже
  выданные награды пересчёт не затрагивает), ручная корректировка баланса (с обязательной причиной в лог),
  разбор заявок на пополнение, разбор заявлений о разбане, обнуление аккаунта.
- **Сервер** (5 уровень): состояние игрового сервера (питание, процессор,
  память, диск, аптайм), запуск, перезапуск, остановка и консольные команды
  через API панели хостинга. Останов, перезапуск и «убить процесс»
  подтверждаются вторым нажатием. Ключ панели хостинга живёт только в
  переменных окружения сайта (`GAME_PANEL_URL`, `GAME_PANEL_KEY`,
  `GAME_PANEL_SERVER_ID`) — в базу и в браузер он не попадает.

Каждое действие в панели пишется в `audit_log` — без исключений, включая
просмотр карточки игрока.

## Панель администрации

Адрес: `/panel` на домене сайта.

Вход двухступенчатый: обычная сессия сайта плюс отдельное подтверждение
паролем на `/panel/login`. Подтверждение живёт 12 часов и хранится в самой
сессии, поэтому угнанная cookie не открывает панель сразу.

Администраторы могут привязать TOTP (Google Authenticator, Aegis) в разделе
«Безопасность» — тогда вход в панель требует ещё и код из приложения.
Chief administrator видит там же список администрации без подключённой 2FA.

Разделы: обзор с метриками и лентой действий, аккаунты с поиском и карточкой
игрока, логи с фильтрами, подозрительные срабатывания, промо- и бонус-коды,
заявки партнёров, пополнения (5 уровень), разбаны (5 уровень), новости
(5 уровень), сервер (5 уровень), персонал (5 уровень), безопасность.

Почта и полный список IP игрока видны с 4 уровня — рядовому администратору
они для работы не нужны.

## Новости

Раздел `/news` на сайте и лента на главной. Публикуются из панели
(`/panel/news`, только chief administrator): заголовок, короткое описание,
текст, флажки «опубликовать сразу», «закрепить сверху» и «объявить в игре».

Адрес страницы формируется из заголовка транслитом: «Открытие сервера» →
`/news/otkrytie-servera`. Совпадающие заголовки получают короткий хвост, чтобы
адреса не конфликтовали.

Новость с флажком «объявить в игре» забирает плагин: раз в минуту он
опрашивает `/api/mc/news`, рассылает объявление в чат и подтверждает доставку
отдельным запросом. Поэтому объявление не потеряется при рестарте сервера и не
повторится дважды.

Черновики (снятые с публикации) на сайте отдают 404 и не видны в списке.

## Сезон и события

Сервер живёт сезонами: название («Season I») выводится в списке игроков рядом
с TPS, временем тика, онлайном, пингом и балансом игрока.

**Искры сезона** — событие в мире: раз в несколько минут рядом со случайным
игроком вспыхивает сгусток частиц, о котором узнают все в радиусе 250 блоков.
Кто добежал первым, забирает награду: 45 % искр дают 5–250 VC, остальные —
25–500 осколков. Награду начисляет сайт, он же держит потолок в 12 искр в час
на аккаунт: событие в игре не должно уметь печатать валюту.

## Оформление

Тёмная тема с тонкими фоновыми кривыми, мягким свечением и акцентами
золото/мята. Анимации: появление блоков при прокрутке, счётчики чисел,
блик на кнопках, подсветка активного раздела, «дыхание» индикатора онлайна.

Всё сделано на CSS и одном IntersectionObserver — без анимационных библиотек.
При `prefers-reduced-motion` анимации выключаются, а без JavaScript блоки
показываются сразу: класс `js` на `<html>` ставится инлайновым скриптом до
первой отрисовки.

Панель использует тот же язык: карточки, надзаголовки, счётчики и боковая
навигация с подсветкой активного раздела.

## Telegram-бот

Бот `@VanillaCraftx_bot` связывает аккаунт сайта с Telegram. Токен живёт только
в `TELEGRAM_BOT_TOKEN` — в репозитории его нет и быть не должно: по токену кто
угодно управляет ботом.

Привязка идёт по одноразовому коду: игрок берёт его в игре командой `/tg` или в
кабинете, отправляет боту, бот сверяет и связывает. Код живёт 15 минут, при
выдаче нового прежние гасятся — иначе подсмотренный в чате старый код работал бы
наравне со свежим. Одному Telegram соответствует один аккаунт, и наоборот.

Команды розыгрышей (`/newgiveaway`, `/giveaways`, `/draw`, `/cancel`) открыты не
по списку id, а по праву `giveaways.manage` из рангов сайта. Так админка живёт в
одном месте: сняли право в панели — закрылся и бот. Чтобы ими пользоваться,
администратору надо сначала привязать свой Telegram к своему аккаунту.

Вебхук `/api/tg/webhook` закрыт секретом `TELEGRAM_WEBHOOK_SECRET`, который
Telegram присылает заголовком: адрес публичный, и без проверки на него мог бы
писать кто угодно. Пока секрет не задан, обработчик не принимает ничего —
молча работающий без проверки вебхук хуже неработающего. Отвечаем всегда 200:
на любой другой код Telegram повторяет доставку, и одна упавшая команда
повторялась бы бесконечно.

Регистрация вебхука выполняется один раз:

```
curl -F "url=https://vanillacraft.click/api/tg/webhook" \
     -F "secret_token=$TELEGRAM_WEBHOOK_SECRET" \
     "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook"
```

## Мост чата с Telegram

Общий игровой чат уходит в группу `TELEGRAM_CHAT_ID`, а ответы оттуда попадают
обратно в игру. Обе стороны обслуживает один запрос `/api/mc/chat`: плагин
присылает накопленные строки и тем же ответом забирает то, что написали в
Telegram, — одного таймера хватает на оба направления.

Пересылается только общий чат (сообщения с `!`). Местные разговоры остаются
местными: в Telegram они шли бы потоком без контекста, а радиус на то и радиус.

Строки уходят пачкой раз в пять секунд, а не по одной: Telegram ограничивает
частоту сообщений в группу примерно двадцатью в минуту, и живой чат выбил бы
лимит за полминуты. Каждая строка рисуется как `🎮 <b>Ник</b>` и текст с новой
строки — видно, кто написал. Текст экранируется: игрок может отправить что
угодно, а сообщение уходит с `parse_mode=HTML`.

Обратно берём только ответы на сообщения самого бота — обычная переписка в
группе игроков не касается. В игре такое сообщение помечено `[TG]` и именем
ответившего. Очередь ответов лежит в `GameChatMessage` и помечается доставленной
в том же запросе, поэтому одно сообщение не покажется дважды.

Кто может писать в игру, решает состав группы: любой её участник, ответивший на
сообщение бота, будет услышан всем сервером. Поэтому группа закрытая, а состав
держит сам бот.

**Заявки на вступление.** Обновление `chat_join_request` бот разбирает сам:
привязан Telegram к игровому аккаунту — принимает, не привязан — отклоняет.
Человеку сначала пишут решение и, если отказ, что делать (`/tg` в игре), и
только потом обрабатывают заявку: личный чат из заявки живёт лишь до этого
момента. Заявки в другие чаты игнорируются. Каждое решение пишется в журнал.

Заявки приходят на вебхук наравне с сообщениями, но если `allowed_updates` был
задан явно, `chat_join_request` в списке может не оказаться — тогда бот их
просто не увидит. Регистрация с обоими типами:

```
cd /opt/vanillacoins/deploy && TGTOKEN=$(grep -m1 '^TELEGRAM_BOT_TOKEN=' .env | cut -d= -f2-) && TGSECRET=$(grep -m1 '^TELEGRAM_WEBHOOK_SECRET=' .env | cut -d= -f2-) && curl -sS -F "url=https://vanillacraft.click/api/tg/webhook" -F "secret_token=$TGSECRET" -F 'allowed_updates=["message","chat_join_request"]' "https://api.telegram.org/bot$TGTOKEN/setWebhook"
```

Боту нужно право «Добавлять участников» в группе — без него он не сможет
принимать заявки.

## Награда за голос в мониторинге

Обратного вызова у top-minecrafter нет — есть выдача последних голосов по
ключу, поэтому мы их опрашиваем:

```
GET https://public-api.top-minecrafter.com/v1/servers/<id>/votes?page=1&limit=50&key=<ключ>
```

Расписание берём от плагина: он и так ходит на сайт по таймеру
(`votes.poll-seconds`, по умолчанию 5 минут), и заводить ради одного запроса
cron на VPS незачем. Плагин только будит `/api/mc/votes` — начисляет сайт.

Награда: `rewardVc` за сам голос плюс `streakBonusVc` за каждый день серии
сверх первого. По умолчанию 200 и 10, то есть первый голос — 200 VC, серия из
трёх дней — 220, из десяти — 290. Серия приходит от мониторинга полем `streak`.

Три защиты, без которых это раздавало бы VC:

- **Повторы.** Своего идентификатора у голоса нет, поэтому ключом служит ник и
  время: проголосовать дважды в одну секунду нельзя. Уникальный индекс в базе —
  единственный арбитр, гонка двух опросов ничего не удвоит.
- **Задним числом.** Голоса старше `maxAgeHours` (48 ч) не оплачиваются: иначе
  первый же опрос после подключения раздал бы награды за всё, что видно в
  выдаче.
- **Бесконечная серия.** Прибавка считается не дальше `streakCap` (30 дней):
  серия растёт сама, и без потолка голосующий год подряд получал бы тысячи VC
  за один голос.

Ник ищем и без учёта регистра: на сайте мониторинга его пишут как придётся.

Ключ и суммы лежат в настройках (`/api/panel/votes`, право
`payments.providers`), поверх значений из окружения — менять их через передеплой
сайта лишняя работа. Наружу ключ отдаётся только маской. За начислением следом
идёт поручение `VOTE_REWARD`: игрок видит спасибо в игре, а не молча выросший
баланс.

## Пароли и что с ними может администрация

Посмотреть пароль игрока нельзя — ни с пятым уровнем, ни с любым другим. В базе
лежит argon2id-хеш (`memoryCost` 19 МиБ), самого пароля там нет ни в каком виде,
и восстановить его из хеша невозможно. Это не настройка прав, а устройство
хранения, и менять его мы не будем: тогда утёкшая база выдала бы чужие пароли —
а люди повторяют их на почте и в других играх.

Вместо просмотра есть выдача нового пароля: право `users.password` (5 уровень),
кнопка в карточке игрока. Пароль генерируется на 16 символов без похожих букв,
показывается один раз тому, кто выдал, и больше нигде не хранится в открытом
виде.

Обставлено так, чтобы этим нельзя было пользоваться незаметно:

- ник цели вписывается руками — промах мышью не выкинет человека из аккаунта;
- аккаунт того же уровня или выше не трогается, как и при обнулении;
- все сессии игрока закрываются, иначе смена пароля ничего не закрывает;
- действие пишется в журнал;
- если у игрока привязан Telegram, бот сразу сообщает ему о смене.

## Восстановление пароля

Почту сайт не отправляет — транспорта нет, и «мы выслали письмо» было бы
обманом. Код уходит в Telegram-бота: туда, где человек уже подтвердил, что
владеет аккаунтом. Без привязки восстановиться самостоятельно нельзя, и на
странице это написано прямо.

Ответ на заявку одинаковый всегда — есть аккаунт, нет аккаунта, привязан
Telegram или нет. Иначе по нему перебирались бы занятые логины.

Код шестизначный и живёт 15 минут. В базе лежит его хеш: утёкшая база не должна
давать вход в чужие аккаунты. Перебор закрывается не задержкой, а сжиганием —
после пяти неверных попыток код удаляется. Заявки ограничены и по адресу, и по
логину. После смены пароля все сессии игрока закрываются: та, из которой пароль
увели, тоже.

Код можно получить и прямо в боте командой `/reset`.

## Обновление сайта

Полная выжимка всех команд — в `docs/DEPLOY.md`. Коротко: одна команда на VPS,
из-под root:

```
bash /opt/vanillacoins/deploy/update.sh
```

Скрипт сам подтягивает ветку `claude/minecraft-server-demorgan-16y10o`, чистит
кэш сборки и старые образы, проверяет остаток места, накатывает схему базы
(`prisma db push`) и пересобирает контейнер сайта. Другая ветка — через
переменную:

```
BRANCH=main bash /opt/vanillacoins/deploy/update.sh
```

Ничего разбивать на отдельные команды не нужно: именно склейка нескольких строк
в одну ломала прошлые деплои. Тома с базой скрипт не трогает — `docker system
prune --volumes` и `docker volume prune` на этой машине запускать нельзя, они
сносят том `pgdata` вместе с базой.

## Скин из кабинета

Сервер в offline-mode, скины раздаёт SkinsRestorer. Он умеет брать текстуру по
ссылке, поэтому картинку храним у себя (`PlayerSkin`, байты в базе) и отдаём
публично на `/api/skins/<ник>.png`, а в игру уходит адрес.

В кабинете два режима: своя картинка (PNG 64×64 или 64×32, до 100 КБ) или скин
чужого ника. PNG проверяем сами — подпись и размеры из заголовка IHDR: ради
двенадцати байт тащить графическую библиотеку незачем.

Дальше работает поручение `APPLY_SKIN`. Плагин своей реализации скинов не имеет
и просто отдаёт команды SkinsRestorer от консоли: для картинки —
`sr createcustom <имя> <ссылка> <модель>` и `skin set <имя> <игрок>`, для ника —
`skin set <ник> <игрок>`. Имя скина несёт время правки, иначе SkinsRestorer
отдал бы прошлую картинку из своего кэша. Модель (classic или slim) задаётся
только для своей картинки: у чужого ника она приезжает вместе со скином.

Новое поручение вытесняет прежнее недоставленное — в игре нужен последний
выбор, а не очередь из всех нажатий.

## Рулетка: ставка на сектор

Игрок выбирает множитель и ставит на него: выпал — ставка умножается, не выпал —
сгорает. Раньше выплату получали все, кто поставил, и средняя выплата колеса
была 2.93 ставки — сайт отдавал втрое больше, чем принимал.

Раскладка пересобрана под новую механику: 41 сектор — 18 по x2, 12 по x3, 7 по
x5 и 4 по x10. Доли подобраны так, чтобы средняя выплата по каждому сектору была
меньше ставки (0.88 у x2 и x3, 0.85 у x5, 0.98 у x10) — сектор, выгодный игроку,
медленно опустошал бы казну, и ставили бы только в него. Одинаковые множители
разведены по кругу с учётом стыка через ноль: колесо круглое, последний сектор
соседствует с первым.

## Место на диске

У VPS диск 10 ГБ, и деплой — самая прожорливая операция: сборке нужно около
двух гигабайт под слои. Когда место кончается, падает не только сборка:
Postgres останавливается на первой же неудачной записи (`PANIC: could not
write to file ... No space left on device`) и уходит в цикл перезапуска, а
сайт отдаёт 500 на всех страницах, которые читают базу.

Что съедает диск:

- кэш сборки buildkit — растёт с каждым деплоем;
- прошлые образы сайта: каждая пересборка оставляет предыдущий;
- json-логи контейнеров — докер их по умолчанию не ротирует.

Поэтому `deploy/update.sh` перед сборкой чистит кэш и брошенные образы,
обрезает логи контейнеров и проверяет остаток: меньше 1.5 ГБ — деплой
останавливается, не доводя до падения базы. В `docker-compose.yml` у всех
сервисов включена ротация логов (10 МБ × 3 файла).

Когда место кончилось — уборка одной командой:

```
bash /opt/vanillacoins/deploy/cleanup.sh
```

Он чистит кэш сборки, неиспользуемые образы, остановленные контейнеры, логи
контейнеров, журнал systemd, кэш apt и ротированные логи — то есть только то,
что пересоздаётся само, — и показывает, сколько освободилось. Логи контейнеров
именно обнуляются, а не удаляются: докер держит их открытыми, и удалённый файл
занимал бы место до перезапуска. Посмотреть, кто съел диск, не удаляя ничего, —
`deploy/diskcheck.sh`.

После деплоя `update.sh` убирает за собой две крупные вещи: образ мигратора и
кэш сборки. Мигратор — это стадия `builder` со всеми зависимостями и
исходниками, полтора-два гигабайта, и между деплоями он не нужен. Перенести
миграцию в рабочий образ нельзя, хотя соблазн есть: `prisma db push` тянет
зависимости CLI, а в рабочем образе лежит только клиент — проверено, падает на
`@prisma/config`. Кэш сборки тоже чистится после деплоя: следующая сборка будет
дольше, зато у базы есть куда писать.

У `web/` есть `.dockerignore`: без него контекст сборки уезжал демону целиком, а
`COPY . .` клал в слой образа локальные `node_modules` — заодно перетирая чистые
из стадии `deps`.

Тома скрипты не трогают ни при каких условиях: `docker system prune --volumes`
и `docker volume prune` на этой машине снесут том `pgdata` вместе с базой.

Посмотреть, что занимает место: `bash deploy/diskcheck.sh`. Тома
(`docker volume`) не чистятся никогда и ничем автоматическим — в них база.
